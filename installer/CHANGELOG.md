# FEA Studio – Changelog

Upgrade: run setup.exe (Windows) or `.run` (Linux) over the existing installation, or extract a new archive and run `Install FEA Studio.bat update` / `./install.sh update`. The installer applies migrations (`installer/migrations.py`), removes obsolete files, and synchronizes modules.

## 1.5.1 (2026-11-26)

The first release after 1.4.1. It contains everything of the 1.4.2 release candidate (never published; its section follows) and the work below. Verification of the release: the public verification page (`docs/verification/`, run with the shipped Windows `ccx_spooles.exe`): 115 of 117 cases within tolerance (479 checks listed), none outside; K2 (mortar contact, Linux only) and KK4 (an impact of about 4 h) not run and listed as such; SM1 (submodel peak) is at 4.74 % against its tolerance of 6 % (owner decision of 26. 11. 2026, was 5 %); Linux (WSL2, shipped `ccx_spooles`): all 192 cases / 1 237 check values with SPOOLES and with faer, no case with an error; SM1 is at 5.12 % there, within the 6 % (outside the former 5 %), and no other check was outside its tolerance.

### Installer, licences and help: fixes of the review before the release
- **Linux updates replace the solver**: an update kept the `ccx_spooles` of the previous version for ever; it is now compared with the package (program and libraries) and replaced like on Windows; a `ccx_pastix` that you built is never touched.
- **Updates without internet**: the new CalculiX is unpacked before anything is downloaded (it needs no network), and the old Intel files are removed only after the new packages and solver are in place.
- **Four help chapters were missing** in the program and in every manual (Contacts, Friction, Members, Supports); the HTML, PDF and Word manuals have no dead links any more.
- **Licences**: the LGPL-3.0 (and GPL-3.0) texts go with PySide6 and shiboken6, used under the LGPL-3.0; the generated licence documents name the files the packages really carry; the packages' file lists include the Windows source archives of CalculiX.
- **Module lists**: setup.exe over an older installation no longer adds Exudyn because of `ngsolve` (the old solver module becomes `direct`, as with the zip / .run update; `ngsolve` now needs `motion`, which is said when it is added), the printed list is the installed one, updates of a standard installation add the new module `sketch`, and the setup.exe component page follows the installed modules.
- **Uninstall** also removes the MCP registrations of this installation from AI clients.
- Smaller: the zip installation refuses network folders and too long paths like setup.exe; the `.run` refuses unknown options before extracting and speaks English or Czech; `--lang` switches the installer's language; the launchers ignore PYTHONHOME / PYTHONPATH of other programs; a start of the GUI without the module `gui` says how to install it; the Linux uninstall rebuilds the MIME database.

### CalculiX equation solver on several threads again (F17 stage A)
- **The own `ccx_spooles` (Windows and Linux) factorizes with SPOOLES on the threads of the job**; the triangular solves stay on one thread (the parallel solve of SPOOLES is a data race – wrong eigenvalues and buckling factors from 3 threads on – and is replaced by the serial one). A ccx gets several equation-solver threads only when `ccx -v` prints BOTH `FEA_SPOOLES_FACTOR_CHECK=2` and `FEA_SPOOLES_ORDERED_ASSEMBLY=1`; any other binary (an older build, a third-party one) keeps one thread. `FEA_SPOOLES_THREADS=N` caps the threads, `1` gives one equation thread (bit for bit the same results from run to run). This replaces the rule "SPOOLES on one thread".
- **Why two safety measures.** The multi-threaded factorization of SPOOLES can rarely LOSE an update (one chunk of a front is not added; reproduced to the last printed digit: 7.2e6 instead of 6.5e5 for the first eigenvalue of a cantilever, 3.97e7 instead of ~0 for a rigid-body mode of a cyclic sector; no message; 7 wrong runs in about 3 800 runs of an unprotected build). (1) The sums of a front are made in a fixed order and the hand-over of the chunks between the threads is locked and counted (patch of SPOOLES, `spooles_2.2_ordered_assembly.patch`). (2) EVERY multi-threaded factorization is checked by a test solve (row-wise backward error, limit 1e-12, about 1e-16 for a correct factorization; one solve and one matrix-vector product) and repeated with the same threads and then on one thread when the check fails (`ccx_2.23_spooles_serial_solve.patch`; GPL-2.0, dated change notices in the changed code).
- **What you see.** Nothing in a correct run (the check has never fired in the gates). When it fires, the results carry ONE note (EN + CS): the factorization was repeated and the final factors passed the check; or – when the test solve of the final factors could not be done (memory) – that the results were not verified; or – when the factors fail the check also on one thread – that the matrix (nearly singular, badly scaled) is the cause and the results may be inaccurate. The raw lines stay in the ccx log.
- **Results depend on the number of threads** (the order of the sums is fixed per thread count, not across counts): eigenvalues differ from the one-thread run by at most 8e-7 relative (the 7 printed digits), the static fields of the V12 jobs are identical in the 6 digits of the `.frd`; repeated runs with the same thread count are bit-identical.
- **Speed and memory** (ccx only, 8 OpenMP threads, 1 / 4 / 8 equation threads, median of 3): static V1 52 k nodes 36.9 / 22.9 / 20.7 s, 122 k nodes 177 / 105 / 91 s, modal M1 22 k nodes 13.1 / 11.0 / 10.9 s, contact K1 21.8 / 15.6 / 14.5 s; peak memory +2 … 4 % (V1 122 k nodes 2.91 → 3.01 GB; the small K1 +53 MB).
- **Gates of the shipped Windows binary** (`ccx_spooles.exe`, SHA-256 `c2532a06...`, built from the pinned toolchain; two builds gave the same program): stress gate of SPOOLES 1 023 runs of eigenvalue, buckling and static decks at 1, 4 and 8 threads against the one-thread reference, 0 wrong, 0 check notes; stress gate of faer 294 runs, 0 wrong; the check-forcing test (limit 1e-30) repeats, takes the verdict "the matrix, not the threads" and gives right eigenvalues; full verification suite 176 cases / 1 036 check values with SPOOLES and with faer, 0 failed checks (two cases need the direct solver module, which the build machine did not have). **KK2** (snap-fit hook, friction, NLGEOM) is bistable at round-off level – assembly force W = 1.43798 N on one equation thread, 1.43854 N on 4, 1.42961 N on 8 (0.16 / 0.12 / 0.72 % from the closed form, each reproducible) – not a solver defect; **decided by the owner (25. 11. 2026):** the two checks on W ("W/P" and Bayer's W from P – one quantity) have the tolerance 1 % (was 0.5 %), no thread cap; all values pass. **Number of modes of a free body:** the full 360° ring of the cyclic-symmetry case CY2 can list 34 instead of 35 modes at 8 equation threads – ccx prints a rigid-body mode only when its noise eigenvalue (about 1e-4) comes out positive; the 34 physical eigenvalues are identical to the reference.
- **Linux gate of `ccx_spooles` (25. 11. 2026, WSL2, rebuilt binary, after the merge of the Windows optimisations):** 273 SPOOLES runs (4 / 8 / 16 threads) and 99 faer runs of the five eigenvalue / buckling / static decks, 0 wrong, 0 failed, 0 check notes. A Linux installation has no MYSTRAN binary (the cross-checks F9M / F3M / F11M need one built from source or downloaded) and Chrono only with the module `motion`.
- **Full verification on Linux (26. 11. 2026, WSL2, final 1.5.1 code, `ccx_spooles` SHA-256 `4c032685...`):** all 192 cases (1 237 check values) with SPOOLES and with faer: no case with an error. One check was outside the limit of that time in each run, the same one: SM1 submodel peak 32.93 MPa, 5.12 % against 5 % (the Windows run gives 32.82 MPa, 4.74 %; the same value with SPOOLES and with faer, so not the solver; most likely a slightly different Gmsh mesh on Linux, not compared). With the tolerance of 6 % of the owner decision of 26. 11. 2026 it is within its limit (the Linux run was not repeated: only the limit changed). The 117 published cases all ran (K2 mortar contact and KK4 included, which the Windows page does not run): 116 within tolerance. SPOOLES and faer agree in 1 110 of the 1 237 values to all printed digits. ### FEA_THREADS caps the total CPU use of concurrent CalculiX work
- **`FEA_THREADS` now also limits the number of concurrent CalculiX jobs** (owner decision of 25. 11. 2026). With it set, (concurrent ccx jobs) × (threads per job) <= `FEA_THREADS` everywhere the program starts several ccx at once: the plan of the load states (`ccx.parallel.plan`; `FEA_THREADS=4` gave "7 CalculiX jobs × 1 threads" because it counted the 8 logical processors, now at most 4 jobs × 1 thread, or 2 × 2 for two states), the shares of independent jobs (`ccx.concurrent`: natural frequencies + buckling, Campbell speeds, print variants), eigen / dynamics beside the load cases (`side_jobs`, also beside the direct solver) and the nonlinear contact branches. Thermal states and the creep of printed parts, which used to run in the background beside the mechanics with all threads, are computed in order. **With `FEA_THREADS` set, runs with many load states can take longer than before** (V1 with 7 load states on 8 cores / 16 logical processors, 22 k nodes: 15.5 s with the default "7 jobs × 2 threads", 25.4 s with `FEA_THREADS=4` = "4 jobs × 1 thread"; displacements and stresses differ by at most 1.3e-7 relative, the last printed digit of the `.frd`); without `FEA_THREADS` nothing changes. `FEA_CCX_PARALLEL=0` still means one job at a time. Help page "Solving" (also in Czech), tests `tests/test_ccx_parallel.py`, `tests/test_ccx_concurrent.py`.
- **What the cap covers (review round).** CalculiX jobs of every kind; the thermal states (their pool is sized from the threads of its share, so print variants × thermal states no longer give 16 threads under `FEA_THREADS=4`); the threads of the direct solver and its assembly worker (a larger `solver.nproc` of a study file or an option of a caller is cut to the share, it used to override the cap); the MPI processes of the iterative hypre solver (same rule); a stray `OMP_NUM_THREADS` / `CCX_NPROC_*` in the shell no longer raises the threads of a serial ccx job (with `FEA_THREADS` the program sets them); the MYSTRAN cross-check script runs at most `FEA_THREADS` processes at once. NOT covered: meshing (Gmsh), picture rendering for the report and other programs outside the solvers. `FEA_CCX_PARALLEL=0` now also computes the thermal states one after another (the help sentence was wider than the code). `FEA_THREADS` is read with whitespace stripped and ASCII digits only (a value such as `²` is ignored instead of raising). Creep computed in order (with `FEA_THREADS`) no longer moves the progress bar back and is booked under the phase "Finishing / 3D printing: creep" instead of the mechanics. Without `FEA_THREADS` nothing changes. Tests in `tests/test_ccx_parallel.py`.
### Space model checks: no repeated solver work (S4 optimisation)
- **Check 3 (unit displacements) = one assembly and one factorization** for the six unit states (it was six: the states constrain the same DOFs, only the prescribed values differ). `assembly.assemble` takes the prescribed values `g` as one column per state (rigid remote supports: the values of their extra DOFs in the rows of `g`); `_checks_static.solve_prescribed` groups the states that constrain the same DOFs (only with the own assembly; the `FEA_ASSEMBLY=ngsolve` fallback solves them one by one as before; each state keeps its own backward error). The displacements, stresses and reactions equal those of the single-state solves (test `test_the_unit_states_share_one_assembly…`: U ≤ 1e-12, S, RF ≤ 1e-9 relative). Check 4 prepares the constraint plan of its model once instead of twice. (Check 3 is the direct path only – on a ccx-only installation it is skipped as before.)
- **The PCB (Steinberg) check computes the modal basis once** for all components of a report (it re-ran the whole modal analysis for every component); the RMS displacements are bit-identical. The basis for it and for the effective-mass check (`run_basis(..., with_stress=False, with_reactions=False)`) is built without the modal stresses and reactions, which neither of them reads (the frequencies, shapes, participation factors and effective masses are bit-identical; the mode-equilibrium entry of the basis checks is then empty, "not checked"; on the direct path the element matrices are not built either).
- **Check 6 (mesh convergence) takes level 1 from the results of the study** when they prove it: the digest of the study state (`Results.info["study_digest"]`, set by `run_study`, not saved to files) equals that of the checked study, the mesh is the same (object or content, including its edge / point selections and tie table), the load cases are the same and none of them is a partial nonlinear result, and – when frequencies are followed – the study has a plain frequency window with at least as many modes as followed. Any doubt = the level is solved as before. The digest is taken when `run_study` is entered. The frequencies are then those of the study's own run (its mode count may be larger than the followed one: the first `n` of them are used with the same rigid-body cut as the full path; equal to the solver tolerance, not bit-identical).
- **`static_solutions` (static correction of the dynamics, ccx basis) runs its states as concurrent ccx jobs** (`ccx.parallel`, as the load cases of a study; `FEA_CCX_PARALLEL=0` keeps one job); equal to ~1e-9 (measured on 3 states of a 2.5 k node model: displacements ≤ 2.4e-10, stresses ≤ 5e-12 relative to the maximum; reactions identical).

### Owner decisions of 26. 11. 2026 (release 1.5.1)
- **MYSTRAN is no longer bundled.** No package carries `tools/mystran/mystran.exe` (its static program has libquadmath (LGPL-2.1), SuperLU, METIS / GKlib, the GCC run-time and BLAS / LAPACK inside, whose sources and licence texts the packages did not have), and the packaging refuses to build with a MYSTRAN program in it. For the cross-checks (V1–V7, V5, F9M, F3M, F11M; the buckling of frames with the CalculiX U1 solver) download it yourself from https://www.mystran.com and save it as `tools/mystran/mystran(.exe)`; without it they say "not run – MYSTRAN not installed", the public verification page marks such a run accordingly, and the module `verify` installs without it. The committed page keeps the MYSTRAN rows of its run. Removing the module `verify` no longer deletes `tools/mystran` (it holds your download). **An update from a version older than 1.5.1 removes the previously bundled MYSTRAN** (the licences of the libraries inside its program): it deletes `tools/mystran/mystran.exe` (Linux `tools/mystran/mystran`) and then the folder if it is empty – other files you put there stay, and nothing is deleted through a junction or symbolic link. Download MYSTRAN yourself if you want the cross-checks; a copy you save after the update is not touched by a later update or repair. If you had put your own MYSTRAN under these names before the update, it is removed too – download or copy it again. When every selected verification case is skipped (MYSTRAN missing), `verification.run_all` now says that nothing was checked instead of “all checks passed”.
- **Sources are always included; there is no written offer.** The Windows and Linux packages carry the sources in `licenses/sources/`, and the "written offer" is gone from `licenses/SOURCES.md` and the licence notes. A build that leaves sources of its binaries out (`make_package.py --no-runtime-sources`, `--with-ccx-pastix`) is a development build: all its files are named `…-dev`, its `licenses/SOURCES.md` starts with NOT FOR DISTRIBUTION and the build log says so.
- **Linux packages carry all sources (like the Windows ones; GPL §3(a) / GPLv3 §6) instead of relying on the written offer.** `licenses/sources/` of the `.tar.gz` / `.run` now holds the sources of everything in the Linux `ccx_spooles` and its `lib/`: CalculiX, SPOOLES with the correction of dhondt.de, ARPACK-ng 3.9.1, LAPACK 3.12.0, `rust-src` and the 118 crates of faer, and for libgfortran, libgcc (linked in), `libgomp.so.1` and `libquadmath.so.0` (shipped) the GCC 16.2.0 archive that the pinned conda-forge toolchain is built from (`installer/linux/ccx_gccsrc.lock`) with the conda-forge recipe and patches taken from the pinned `libgomp` package. `make_package.py` refuses a recipe that does not name the pinned archive. `SOURCES.md` has the table and how to rebuild or replace a library; the written offer is only a fallback. The Linux packages are about 230 MB larger (173.5 MB → 403.7 MB; the GCC archive is 193 MB of it). The Windows packages carry the same files as before (their `SOURCES.md` is the shared one).
- **SM1 (submodel peak):** the tolerance of the check of the submodel stress peak against Peterson / Heywood is 6 % (was 5 %). The peak depends on the mesh that Gmsh builds on the platform: 4.74 % on Windows, 5.12 % on Linux (the same value with SPOOLES and with faer). The public verification page was regenerated from the stored results of the 1.5.1 run with SM1 run again (shipped Windows `ccx_spooles.exe`, same values); only the limit changed.

### Setup confirmation before an AI calculation (F15-S1)
- **New core tool `fea_setup_review`**: one numbered picture (every support, load and thermal condition has a number badge, the legend rows are the table rows) and a table (number, kind, selection, faces with count and area, value with units, cases) of what will be computed, plus a **digest** (SHA-256) of the whole setup – geometry file, materials as assigned, selections and the faces they resolve to, supports, loads, thermal cases, contacts, bolts, welds, mesh settings. Renaming a selection, material or load case keeps the digest; a changed value, face, material, mesh size or geometry changes it. The same digest function (`fea_core/mcp/setup_proof.py`, `setup_digest`) is meant for the ECSS report (F14-S6).
- **`fea_solve_run` and `fea_job_start(kind="solve")` can require the user's confirmation** (parameter `confirmed=<digest>`): **on by default in the program window** (Tools → "Ask before an AI calculation", stored in the settings), **off for a headless server** (`--confirm` or `FEA_MCP_CONFIRM=1` turns it on). The user is asked by the best available way: the **window** opens a non-modal dialog (numbered picture, table, Confirm / Reject, a click on a row shows its faces in the 3D window; only the click counts and a setup changed after the review is not confirmed), otherwise an **MCP client with elicitation** gets a yes / no question with the table, otherwise the **agent fallback**: the agent passes the digest back after asking in the conversation, recorded honestly as `confirmed_by: "agent"`. The calculation is refused with an instruction to the agent when the setup is not confirmed or the digest is stale; the digest is checked again under the session lock just before the solver starts. The window's own calculations (Run) never ask.
- **Recorded and reported**: who confirmed (user in the window / user through the MCP client / agent), when, and the digest are stored in `Results.info["setup_confirmation"]` (saved with the results) and printed in the Word report (section "Setup confirmation" with the numbered picture and the table).
- Order for an agent: mesh first (`fea_mesh_generate` changes the mesh settings, which are part of the setup), then `fea_setup_review`, then the calculation.
- The same gate (`confirmed=<digest>`) stands before the other tools that start solver runs: `fea_mesh_convergence`, `fea_param_study_run`, `fea_sweep_run`, `fea_submodel_run`, `fea_topo_opt_run`. Not covered: fatigue, 3D-printing variants, mechanisms. An elicitation that the client declared and then failed is an error (the digest passed back is not taken as the user's answer); the report reads only the stamp in the results (a stamp read from a saved file is marked as such). The digest follows every reference by name (`buckling.case`, the material of a bar, the master of a conductance, ...): it stands for the content of the item, so swapping the names of two load cases changes it (digest scheme 2).
- Tests: `tests/test_setup_proof.py`, `tests/gui/gui_setup_confirm_smoke.py` (Czech and English). Help: the page "Automation" (MCP section), also in Czech.

### Topology optimization: manufacturing constraints (F15-S3)
- **Symmetry, extrusion and overhang in the BESO** – `TopologyOptSpec.symmetry` (up to 3 mutually perpendicular mirror planes), `.extrusion` (a prism along a direction), `.overhang` (build direction or `from_print`, angle, base `min` | selection), `.compare_unconstrained`; GUI: section "Manufacturing constraints" in the Topology dialog (planes from a selected face, orange build-direction arrow in 3D, scrollable dialog); MCP `fea_topo_opt_run(symmetry=, extrusion=, overhang=, compare_unconstrained=)` (group `results`; axis letters `'x'`, `'-z'` accepted); Word report: chapter "Topology optimization" with the table of the constraints, the measured values and the compliance penalty; help (Results) EN + CS. The constraints are pre / post-processing of the density field around CalculiX on the element level of the unstructured tet10 mesh – not a solver. Spec dicts, files and calls without them load and run unchanged (TO1: identical numbers).
- **Symmetry**: every element is joined with the element nearest to its mirrored centroid (tolerance 0.5 x the element size); a group has one decision (sensitivity = volume-weighted mean), a protected element protects its mirror image; elements without a mirror image are counted and decided alone (warning). **Extrusion**: columns of elements of the size of an element (grid aligned with the mirror planes, slivers merged by a kd-tree), one decision per column, a protected element keeps its whole column solid; a mirror plane is applied to the columns (its normal parallel or perpendicular to the direction).
- **Overhang** (APPROXIMATE, stated in the GUI and the report): the rule works on the corner nodes of the elements – a node is supported when a supported node lies below it within 1.5 x the element size in a cone of 90 deg - angle around the build direction, the chain leads to the build plate (BFS over the active nodes, scipy.sparse.csgraph); an element needs all its nodes supported; unsupported elements are removed (cascade), the volume is refilled with the most sensitive supported voids. Two additions to the plan, both needed in the experiments: (1) a support-aware ranking before the threshold (the supporter of a valuable element is not cheaper than what it carries – without it the repair deleted the loaded roofs and the load path broke), (2) a final phase that checks the result with the stricter rule "the support passes through material, not across a thin slit" and re-optimises up to 12 iterations with it (a cone rule alone let the optimiser bridge slits one element thick – a third of the downward area stayed flat); the phase is accepted when its compliance is at most 2 x that of the loop (a warning above 1.2 x), otherwise the loop result stays with a warning. Protected elements count as supported (the number that hang in the air is reported).
- **Robustness of constrained runs**: the best design that reached the target volume is kept (constrained designs chatter), a step that multiplies the compliance by more than 4 (the load path was cut) is taken back with half the removal rate (at most 6 times), a repeating solid set stops the run (`cycle_detected`), `fea_core/topo/results.py` stores the block `info["topology"]["constraints"]` (statistics, checks, penalty, strict-phase figures) in the project.
- **Independent measurements on the exported STL** (not by the optimiser): sections of an extruded result at 3 heights (area spread, overlap), overhang facets (share of the downward area flatter than the angle and than angle - 15 deg, worst facet, 5 % percentile, connected flat patches), mirror mismatch of the result by nearest element; with `compare_unconstrained` the same numbers of the run without the constraint (the compliance penalty).
- **Verification `verification/topo_cases.py`** (ccx 2.23 own build, 1 thread; numbers of the runs on this machine): TO2 symmetry (cantilever 120 x 40 x 20, 4052 elements, mid-plane z = 10): largest density difference inside a mirror group 0 in every iteration, 0.2 % of the elements without a mirror image, mismatch of the result 1.4 % of the volume against 24 % of the run without the constraint, compliance 0.995 x that run (|dev| 0.5 % <= 2 %), volume 50.0 %. TO3 extrusion (100 x 40 x 12, 3874 elements, along z, 65 %): column spread 0 (the run without it 0.999), STL sections at 3 heights differ by 2.1 % in area and overlap 96.5 % (without the constraint 78 %), compliance penalty +21.8 %. TO4 overhang 45 deg (half bridge-type MBB beam 40 x 40 x 4, 4322 elements, built upwards, 60 %): every design element supported (cone + through material), area of facets flatter than 45 deg 28.8 mm2 against 148.6 mm2 without the constraint, largest flat patch 14.4 mm2 (2.7 squares of the element size) against 76.3 mm2, share of the downward area beyond the mesh tolerance 12.8 % against 22.4 %, 5 % percentile of the inclination 25 deg against 13.5 deg, compliance penalty +119 % (strict phase: 10 % of the volume pruned, 12 iterations, 35.2 -> 45.4 N.mm). **Not reached as the plan states it** (no downward facet flatter than 45 deg + tolerance): an element-level rule on an unstructured mesh leaves flat patches of one or two element widths; the case compares with the run without the constraint and bounds the patches in element sizes. At TO1's own settings (120 x 40 x 10, two element layers across the thickness) the symmetric run has 8 % higher compliance than the run without the constraint (2.05 x vs 1.89 x the full design after 40 iterations – the symmetry halves the freedom of the two layers), so the plan's "within 2 % of TO1" holds only with more layers: TO2 uses 20 mm and compares with the unconstrained run on the same mesh.
- **Limits**: the overhang rule needs a filter radius of about 3 element sizes and target volumes that leave room for supports (a 50 % target on the TO4 mesh disconnects the load path – the run reports the compliance); constraints are only for the discrete BESO (not SIMP); unit tests `tests/test_topo_constraints.py` (22), GUI smoke `tests/gui/gui_topo_manufacturing_smoke.py` (EN and CS).

### Equation solver faer inside CalculiX (F17 stage C + D)
- **The own CalculiX (`ccx_spooles.exe` / `ccx_spooles`) factorizes symmetric systems with faer 0.24.4** (Rust, MIT: supernodal Cholesky, LDL^T and Bunch-Kaufman LBL^T, multi-threaded) instead of SPOOLES. The ordering is still the nested dissection of SPOOLES (given to faer as a permutation); the symbolic analysis is kept while the pattern of the matrix does not change (the Newton iterations of a contact analysis: one analysis for all of them). Measured on Windows (8 core notebook shared with other programs, best of two, the same deck, the whole ccx run): linear statics 66 k equations 8.6 -> 5.4 s on 1 thread and 6.8 -> 5.0 s on 4 threads, 117 k equations 22.5 -> 11.0 s and 14.9 -> 9.2 s, 193 k equations 50.9 -> 23.1 s and 33.9 -> 17.7 s, a compact cube of 340 k equations 397 -> 92 s (4 threads), natural frequencies of the 66 k model (31 solves) 17.5 -> 11.2 s, contact K1 (15 k equations, 8 Newton factorizations) 31 -> 16 s; about half the CPU seconds of SPOOLES for the same result. Memory is the same where the model dominates it and smaller where the fill does (Linux, 705 k equations: 7.1 against 11.4 GB, 218 against 576 s).
- **Never a silent wrong answer**: every factorization is checked by a test solve (the row-wise backward error against the matrix that CalculiX handed over, limit 1e-12); a matrix that is not positive definite (shifted eigenvalue problems, buckling) goes down a ladder LDL^T -> LBL^T -> SPOOLES, and a failed factorization or a failed check leaves the system to SPOOLES with a line in the log and one note in the results ("the faer solver could not factorize ...; SPOOLES solved them instead"). ### Surrogate model with calibrated error bars over the parametric study (F15-S4)
- **New: tab "Surrogate model" in Tools → Parametric study**, MCP `fea_surrogate_fit / predict / info` (group `results`), `fea_core/surrogate/`. After a study the program answers "what is the maximum stress / displacement / mass / frequency for these parameter values" in milliseconds as **value with a 90 % band**, and **refuses where no converged analysis exists** (outside the range or the convex hull of the converged points, in a gap, next to a failed analysis; `extrapolate=true` predicts anyway with a warning and no guarantee). Sliders with the live prediction, a curve with its band or a 2D map, a table of the held-out points, "Verify this point with FEM" (one full analysis, compared with the band, added to the training set, refit) and "Suggest next points" (where the model is least informed).
- **The band is split-conformal**: a seeded share of the points (default 20 %, at least 9) is held out of the fit and calibrates the factor (the ceil((n + 1) x 0.9)-th smallest |error| / sigma), so the band holds for new points of the same design in at least 90 % of the cases ON AVERAGE over the analysed region (lower near its edges, which the answers warn about), whatever the regression assumptions. A model is marked **not reliable** (the prediction still comes, with a warning) when fewer than 9 points were held out (nine are the least that can guarantee 90 %; with fewer the band states the level it really guarantees, n / (n + 1), in the GUI, MCP and report), when the R² on the held-out points is below 0.9 (not tested for a practically constant result), or when the cross-validated coverage (leave-one-out) is clearly below the level (below 80 % and below the level minus 1.645 standard errors; the first version used 2.33). **Refused**: too small a training set (4 points per parameter + 2 for the fit and 9 held out; warning below 10 per parameter), a design that does not span the parameters (a line), more than 5 continuous parameters, an unknown category. The bands cover interpolation and mesh noise ONLY – the fixed sentence "not material scatter, manufacturing, other loads or assumptions; the coverage is an average over the region; valid only where analyses exist and for this study" stands in the GUI, the MCP answers and the report.
- **Two backends, one calibration**: Gaussian process (scikit-learn, anisotropic Matern 5/2 + noise, hyperparameters by maximum likelihood with a fixed seed) when the optional module **`surrogate`** is installed, otherwise a scipy radial-basis interpolation (thin-plate spline, smoothing by leave-one-out) with a constant sigma – the conformal factor is model-agnostic. Positive results (stress, displacement, mass, frequency) are modelled in the log space, inputs are scaled to the unit box, a categorical parameter (material, print pattern) gets one model per category. ### Space structures: interface forces, notching, bolts, PCB and rails (F14 S4)
- **Interface forces and moments in the dynamics** (`fea_core/dynamics/interface.py`): the elastic base reaction of the held nodes (constraints and elastic supports) for a base excitation – the modal base-reaction vectors per mode (force and moment about a reference point, default the centroid of the held nodes), the sine force / moment spectrum and the RMS force / moment in random vibration. The static residual of the unit base acceleration makes the f → 0 limit equal to M_total · a_base for any number of modes (checked to 0.5 %; real bar 4e-7). The force is the support force of Newton's law: the elastic reaction plus the damping force of the modes (factor 1 + 2iζf/f_j, at resonance m·a·√(1 + 4ζ²)/(2ζ)); only the HELD components of a held node are summed (a sliding support no longer adds the inertia of its free components; cylindrical supports project on their directions; a node held by several constraints is split between the groups so they add up to the whole), and a model held only by elastic supports works. Groups per constraint and per elastic support.
- **Primary notching / force limiting** (`fea_core/space/notching.py`): the input profile (sine amplitude or ASD) is scaled by min(1, limit / (J · predicted quantity)) for an interface force or moment, the acceleration at a probe, a stress (sine) or a force PSD (random); the minimum notch width and the floor of a notch are rules of the requirement set; notch justification table (unnotched vs notched input, dB reduction, remaining margin, floor-limited / widened), breakpoints simplified from below (the table cannot exceed the limit; it is re-evaluated on a grid ten times finer and the analysis grid refined until it holds) and a CSV export (text cells through `export_csv.text_cell`). A non-finite input or J ≤ 0 is an error, never a verdict; the factor on a PSD limit is J²; probe / stress limits need a base-only harmonic result of one direction and say "at probe X only"; a limit table is applied most restrictively outside its range.
- **ECSS bolted joints** (`fea_core/space/bolts_ecss.py`, beside VDI 2230 in `fea_core/joints/`; adapter `from_vdi_basics`): preload scatter, embedding, thermal preload change ΔF_th from the differential CTE of the clamped stack and the bolt, gapping, slip, bolt tensile (yield, ultimate), shear, combined, thread pull-out (the VDI 2230 stripping capacity of the program; both shear allowables needed) and head / hole bearing; all direct inputs are validated; a missing embedding or thermal data blocks a PASS; The formulas follow ECSS-E-HB-32-23A Rev.1 and carry its clause numbers (see "Space code checked against the ECSS documents" below); no text of a standard is quoted, every factor and coefficient comes from the user-confirmed requirement set, the allowables only from confirmed A / B material allowables.

### One modal basis and three unit-gravity states per study (`fea_core/state_cache.py`, `gravity_states.py`, `direct/modal_cache.py`)
- **The modal basis of a study on a mesh is computed once.** The natural frequencies, the dynamics, the 3-axis launch analysis and the interface forces took the same basis up to four times (assembly + eigenvalue analysis + modal stresses). On the direct path the analysis is stored in the work folder of the run that made it (`<work folder>/state_cache/`: plain `.npy` + `meta.json`, written atomically) and the next analysis of the same study and mesh loads it memory-mapped (the main program keeps no copy of the shapes). One analysis with the LARGER mode count serves the natural frequencies and the dynamics when both ask for the same window (from 0 Hz, the same upper limit); two analyses of one model never run at once (side jobs wait for the first). The modal stresses and reactions are stored too; the interface forces leave the stresses out (`recover_batch(stress=False)`). A CalculiX basis (`ccx` engine) is stored the same way. Key: the study WITHOUT the name, the space settings, the hidden parts, the thread count, the eigenvalue / dynamics / buckling settings and the load cases, PLUS the mesh content, the assembler and the modal engine of the settings, and the rigidly coupled remote loads of the load cases (they add a rigid body to the model). `FEA_STATE_CACHE=0` switches everything off (the previous behaviour).
- **Gravity cases of a linear study are combinations of three unit states.** The 14 signed QSL cases, the unit base accelerations of the dynamics and the unit-gravity statics of model check 1 were solved as separate states (CalculiX: one step each, direct path: one recovery each). Now the three unit states (1 g along x, y, z) are solved once, stored, and every pure global gravity case is made from them; U, S and RF are superposed and go through `make_step` again, so the reactions and the EQUILIBRIUM CHECK are those of the combined state. Applies only when it is valid and saves something: linear study, no contact / NLGEOM / plasticity, no bolts or welds, no beam system, no cyclic symmetry, no thermal states, no 3D printing, no remote support, no prescribed displacement, and at least three gravity cases (or all unit states stored) – everything else is solved as before. If the superposition fails for any reason every case is solved as before (logged). The section forces of a combined state are the same combination of the unit states (`StepResult._combo`).
- **What moves.** Direct path (CubeSat benchmark, rslab): displacements 1e-14, stresses 4e-13, reactions 1e-15 relative to the solved states; the first 12 modes of the shared 14-mode analysis equal a 12-mode analysis to 7e-12 in frequency (the S2F gate is 1e-9) and 9e-10 in the float32 shape; the 3-axis envelopes and the interface forces are identical. CalculiX path: the unit states are the 6 digits of the `.frd`, the combination of rounded numbers differs from a solved state by at most 5e-6 relative (displacement 4.9e-6, von Mises 3.0e-6, reactions 8e-7, 3-axis stress envelope 1.8e-6). **The CalculiX error estimate `stress_error` (STR %, informative) does not exist for a combined state** (it is not linear); the hotspot table and the convergence study show it as not available for such states.

  - *Keys.* A unit state is keyed by the model that was ACTUALLY solved (`state_cache.solved_digest`): the unit statics of the dynamics (a deck of the unit cases alone) no longer share states with a run whose deck also holds a rigid remote load of another case (they differed by 2–26 % in displacement). ### Solvers (F13 steps 0–1: the direct solver without Intel MKL)
- **New direct solver `ngs_direct` = NGSolve + rslab** (pure Rust, MIT, a pip wheel; replaces the MKL PARDISO worker, the stored name `ngs_pardiso` loads as an alias): one analysis and ONE factorization for all load cases, also for a single one. The factor is float64 when it fits into the memory plan and has up to 800 entries per DOF, otherwise float32 refined in float64 by a block conjugate-gradient loop (compact bodies 0.42–0.50× of the PARDISO time, memory −26…−35 %); a float32 factor that does not converge is repeated in float64. Accepted by the backward error ‖r‖/(‖K‖·‖x‖+‖b‖) (the old fixed limit on ‖r‖/‖b‖ rejected correct solutions of thin parts), a matrix that is not positive definite is reported as a free body. ### Constraints on the linear path (F13 step 1b, part 1: studies that went to CalculiX only because of a constraint run with ONE factorization)
- **Run in the direct solver now** (`auto` chooses it, one factorization for all load cases): cylindrical support, elastic support, remote support (rigid and distributing), rigid remote load, *TIE of separately meshed parts, general orthotropic material (Cartesian and cylindrical axes, thermal expansion included) and the statics (weight, inertia) of point masses. **The iterative solver (hypre) takes the node-local ones** (elastic and cylindrical support, orthotropy) – not what couples several nodes (remote supports, rigid remote loads, *TIE, a rigidly coupled point mass): such a study goes to the direct solver or CalculiX, never to hypre. **Still CalculiX:** bolts and welds (next stage), contact and nonlinear analysis, beam structures, cyclic symmetry, orthotropic material together with 3D printing.
- **The constraints are eliminated inside the matrix assembly, not added as equations** (master-slave transformation TᵀKT, the matrix stays symmetric positive definite – no Lagrange multipliers, which the rslab factorization does not accept with its defaults): dependent DOFs u = A·u + c, extra nodes for the reference point of a rigid coupling (displacement + rotation), springs on the diagonal blocks. Checked against the dense matrix written out (1e-12). The equations are the ones written for CalculiX (`cylinder.support_equations`, `remote.distributing_equations`, the quantized stiffnesses of `springs.table`), a rigid face is `*RIGID BODY` (u = u_ref + θ × (x − p), one rigid body per selection).
- **The *TIE is tied exactly as CalculiX does it**, replicated from its source (`gentiedmpc`, `attach_2d`): the master face is split into four flat triangles, a slave node walks over the edges beyond which it lies by more than the in-plane tolerance (0.025 × the mean distance of the centroid from the edge – a physical length), nodes on the border of the master surface stay free (a plain closest-point projection tied three more nodes of the plate with a foot and changed the displacement by 1.7e-3 and the stress by 0.5 of the maximum), then the node is attached to the quadratic master face at its closest point.
- **Orthotropy**: a cylindrical system is rotated at every Gauss point of every element (as CalculiX does; at the centroid the result would differ by about 1e-3), C and the expansion tensor α_ij in the recovery of the stresses (`ortho.ElementField`).
- **Against CalculiX on the same mesh** (cylindrical support V8, V9, elastic support V15, remote supports V7R, V10, *TIE V17, orthotropy V16, a study combining cylindrical + elastic support + prescribed displacement + five states including thermal and weight, two bodies with *TIE + rigid support + two rigid loads on one face + distributing load, point masses, orthotropic bar + ring with expansion): displacements within 6e-7…5e-6, stresses 8e-6…1.3e-5 (the 6 digits of the .frd of CalculiX; 2e-4 at the singular corner of a foot tied to a plate, where recomputing the stress from the displacements of CalculiX itself differs from its stress by 4e-3), reactions ≤ 7e-6, force and moment of the remote supports 1e-7, equilibrium 1e-12. `verification.run_all --backend auto`: V7–V17, T4, T5, TH8B all in `ngs_direct`, 165 / 165 checks.

### Bolts and welds on the linear path (F13 step 1b, part 2: studies with bolts or welds run with ONE factorization)
- **Run in the direct solver now** (`auto` chooses it): bolts of the connection kinds through bolt with a nut, bolt into a thread, countersunk head and clamped stack with a clearance in CAD with the preload state and the thermal elongation, and welds (the forces of the segments, the toe hot-spot, intermittent welds). The iterative solver (hypre) takes welds but not bolts. Still CalculiX: the contact at a bolted joint and every nonlinear analysis, a fitted bolt through parts that touch (the two hole walls share a circle of nodes), and a study whose bearing faces the own assembly would refuse (a face that shares a node with a support, …; the reason is shown) or whose preload the structure cannot carry (a bolt that is the only connection of a part) – then CalculiX continues with a warning.
- **The bolt is an exact Timoshenko beam element between two rigid bearing faces** (one element per distance between faces instead of 64 U1 elements that lock in bending) on the extra nodes of the own assembly; the bearing faces are rigid bodies as before (VDI 2230 assumption). The stiffness of the bolt is the VDI compliance as before.
- **Preload and temperature**: the matrix is the matrix of the continuous bolts (symmetric positive definite, no gap DOF). The thermal elongation α·ΔT·L of a bolt is applied exactly (CalculiX holds it by a penalty spring, error 1e-4); the preload F_V of every bolt is solved on the SAME factorization with one extra right-hand side per bolt (the elongation that gives N = F_V – unit states, solved with homogeneous right-hand sides: no prescribed displacement, no thermal load, as the preload state of CalculiX); the state "Bolt preload" is still last and the load states superpose as before. The cost: 8 right-hand sides at 235 k DOF 0.17 s in the solution phase.
- **Same results structures**: the forces of the bolts (RF − F of the bearing faces and the forces through the joint plane from the stresses at the integration points, now recovered from the displacements instead of printed by CalculiX), the weld segments, `Results.info["joints"]`, the assessment (VDI 2230, EN 1993-1-8, EN 1993-1-9, IIW), the report, the GUI and MCP are unchanged. The properties card and the report show "N bolts as beam elements between rigid bearing faces" and "Bolt preload: N unit states of the elongation of a bolt on the same factorization".
- **Against CalculiX on the same mesh** (S1–S3, lap joint with aluminium plates, preload + shear + weight + two temperature states, two bolts under a rigid remote support / rigid remote load / cylindrical support, bolt into a thread, countersunk bolt through a bundle with a clearance, T-joint with two fillet welds, example 2): displacements 7e-7 … 1.8e-5 (2.6e-4 where the bolt carries the whole shear: U1 is stiffer in shear than the exact element), stresses ≤ 2.9e-5, reactions ≤ 2.4e-6, axial force of the bolt ≤ 0.0011 %, shear force and bending moment of the bolt ≤ 0.12 %, the forces of the weld segments identical, the utilization of every bolt and weld identical to 5 digits (weld fatigue 0.002 %).

### Natural frequencies and the modal basis on the direct path (F14 S0)
- **The natural frequencies and the modal basis of the dynamics are computed without CalculiX where the direct solver can do the study**: the program's own mass matrix (consistent, the 14-point rule of CalculiX's mass, per-element density incl. 3D printing, surface mass, rigid and distributing point masses with rotary inertia), the stiffness of the own assembly with the constraints eliminated (cylindrical / elastic / remote supports, *TIE, orthotropy), ONE rslab factorization of K − σM and the ARPACK Lanczos iteration of SciPy (shift-invert) – no self-written equation or eigenvalue solver. Everything heavy runs in worker processes (assembly, eigen analysis), the program keeps only the modes.
- **No mode can be missed silently**: the number of eigenvalues below a bound is the number of negative pivots of the factor of K − σM (Sylvester); a repeated or clustered frequency that ARPACK missed (or a cluster cut by the number of modes) is searched again with the found modes deflated, and a count that still disagrees is an error (CalculiX then takes over, with the reason). Every pair is checked by its residual and M-orthonormality. Modes by number and by a frequency window (`f_min`, `f_max`), free bodies return their rigid-body modes at 0 Hz.
- **Dynamics**: the modal basis, the participation factors, the effective masses, the modal stresses and reactions and the static corrections of the excitation cases (also the missing mass of a shock) come from the same factor; harmonic, transient, random vibration, shock and sweep fatigue work as before.
- **Which engine**: Solve → Solver → **Natural frequencies** (Automatic / Direct / CalculiX), `Study.solver.modal_engine`, MCP `fea_modal_set(engine=)` / `fea_dyn_settings(modal_engine=)`. Automatic keeps CalculiX for buckling, prestressed modal analysis, the Campbell diagram, cyclic symmetry, bolts (their beam elements of the own assembly have a stiffness but no mass matrix; welds are only meshed bodies and take the direct path), beams, contact and nonlinear states, shells and 2D, when the direct solver is not installed or does not fit into the memory, and for **small problems** (DOF × (modes + 10) below 7·10⁵ – the direct path starts two processes, about 6 s); a failed direct analysis continues in CalculiX with the reason, and a CalculiX run that fails on a small problem (it ends with an error on *TIE together with a normal elastic support) continues with the direct analysis. Results, the Properties and the Word report say which engine computed the modes.
- **Review fixes of the natural-frequency analysis**: a window (`f_min`) just below or above a low mode of a slender model no longer skips modes (the bound moves by a tiny fraction of itself and the count proves that no eigenvalue lies between; a window of a free body starts above its rigid-body modes); a failed accuracy check is repeated with a different shift, driving shift or Lanczos basis; the window means the same in CalculiX and in the direct analysis (the lowest N modes inside it, no phantom 0 Hz modes); CalculiX is replaced by the direct analysis only when it crashes, not for an error it reports about the model, and a takeover is a warning in the results; the rigid-body modes of a free body are 0 Hz and compared the same way on both sides; the main program holds fewer copies of the modes (100 modes × 40 k DOF: 78 → 48 MB peak); the report of the residual says what was checked.
- **Verify with CalculiX** (natural frequencies and dynamics): the same modes in CalculiX on the same mesh, compared by frequency, effective mass and MAC (repeated modes as a subspace) – a table in the results and in the report.
- **Measured** (4 threads, a shared machine, cantilever, wall time / peak memory): 20 modes 66 k DOF 18.8 s against 34.6 s in CalculiX, 142 k DOF 29 s against 94 s, 303 k DOF 67 s (3.1 GB) against 325 s (2.3 GB), 383 k DOF 112 s (4.0 GB) against 580 s (3.1 GB); 100 modes 66 k DOF 37 s against 355 s, 142 k DOF 70 s against 400 s. Below DOF × (modes + 10) ≈ 7·10⁵ CalculiX is faster (11.6 k DOF, 10 modes: 2.1 against 6.6 s) and it needs less memory everywhere. Against CalculiX on the same mesh: frequency ≤ 1e-5 and MAC ≥ 0.9999 for the lowest modes (CalculiX itself is accurate only to its ARPACK tolerance: against the dense solution of the same matrices the direct path has 7e-10 in the frequency, CalculiX 1.6e-4 for 12 modes), the dynamics verification cases M1, M2, Y1 – Y16s all pass on the direct path, combinations of *TIE + orthotropy + rigid / distributing / surface masses and of cylindrical + elastic + remote supports agree to 1e-5 – 6e-5.
- **Fixed in the CalculiX path on the way**: the modes of a free body were paired with the wrong participation factors and shapes (CalculiX numbers them consecutively but leaves the negative eigenvalues – the rigid-body modes – out of its table); CalculiX gives wrong participation factors and total mass for a `*RIGID BODY` with a free rotation node and ends with an error on `*TIE` together with a normal elastic support – the direct path computes both.

### Contacts and nonlinear speed
- **Default penalty stiffness K = 10·E** (was 50·E; λ = K/100 follows, explicit values are unchanged): K6 (bolted joint with a contact interface, slip at 10 kN) needs 188 instead of 255 Newton iterations (643 → 484 s); contact forces differ by less than 0.03 % (Fn 19 228 N, Ft 2 884 N), only the singular edge pressure peak halves (579 → 290 MPa). An **interference (press fit)** keeps 50·E (the stresses of K4 stay 0.03 % from Lamé, with 10·E they would be 0.24 %), and a hard mortar contact keeps the friction stick slope of the former default.
- **Increment control of branch runs is configurable** (Contacts → Nonlinear analysis – steps → Increments (branches); MCP `fea_analysis_set_sequence(increments=)`; the report shows the effective values). Initial and maximum increment are **automatic by the formulation**: 0.25 / 0.5 for surface-to-surface and node-to-surface contact (was fixed 0.1 / 0.25: 17 % fewer Newton iterations on K6, 188 → 156, 412 → 364 s in one session, forces at slip +0.2 %), 0.1 / 0.25 for mortar contact (the Hertz case K2 goes from a 2.5 % to a 5.7 % deviation with larger increments) and for studies without contact. The checks reject dt0 > dt_max, non-numeric values and a non-integer count (also for plasticity-only studies). `fea_analysis_set_sequence`: every argument left out (None) now means "unchanged" (it used to reset kind / branches / stop_keep).
